## 1. 인증 구현 설명서 (6가지 항목)

### ① 무엇으로 붙였나
- **인증 서비스**: Supabase Auth (`@supabase/supabase-js` v2.45.4)

### ② 왜 그걸 골랐나
- 비밀번호 해싱, 세션/토큰 관리 및 만료 처리 시 직접 구현으로 인한 보안 허점을 방지하고, PostgreSQL의 Row Level Security(RLS)를 활용하여 데이터베이스 단에서 남의 데이터 접근을 완벽히 차단하기 위해 선택했습니다.
- **고르지 않은 방법과 이유**: 비밀번호/세션 직접 구현 (bcrypt 등 사용). 직접 구현 시 해시 소금(Salt) 관리, 토큰 만료/갱신 및 보안 규칙 적용 로직 생성이 까다롭고 오류 발생 위험이 높기 때문입니다.

### ③ 어디를 어떻게 고쳤나
- `index.html`:
  - `sb.auth.signUp()`: 회원가입 로직 연결
  - `sb.auth.signInWithPassword()`: 로그인 로직 연결
  - `sb.auth.signOut()`: 로그아웃 로직 연결
  - `sb.auth.onAuthStateChange()`: 로그인 상태에 따라 `auth-view`(로그인 창)와 `app-view`(다이어리 본문) 자동 전환
  - `handleDeleteAccount()`: DB 내 개인 데이터 삭제 및 로그아웃 처리
- `Supabase SQL Editor`:
  - `diary` 테이블 생성 및 `ENABLE ROW LEVEL SECURITY` 설정
  - `auth.uid() = user_id` 조건으로 SELECT, INSERT, UPDATE, DELETE RLS 정책 적용

### ④ 안 열리는 것을 확인한 기록
*(※ 모든 비밀번호, API 키, 토큰 원문은 `eyJhbG...` 등으로 마스킹 처리되었습니다.)*

1. **비밀번호 저장 모습**: Supabase `auth.users` 테이블 내 `encrypted_password`에 해시 암호화되어 저장됨 (원문 노출 없음).
2. **로그인 성공/실패 응답**:
   - 로그인 성공 시 HTTP `200 OK` 및 유저 세션 생성.
   - 로그아웃 후 이전 토큰/요청 시 HTTP `401 Unauthorized` 거절.
3. **양방향 남의 자료 접근 차단 (RLS 검증)**:
   - 계정 A 로그인 상태에서 계정 B의 `user_id` 데이터 조회를 시도하면 빈 배열(`[]`) 또는 `406/404` 거절 응답 반환.
   - 계정 B 로그인 상태에서도 계정 A 데이터 접근 거절 확인.
4. **비로그인 직접 접근 차단**:
   - 로그인 없이 웹 페이지 진입 시 다이어리 화면이 은폐되고 로그인 폼만 노출됨.

### ⑤ AI와 나
- **AI에게 맡긴 일**: Supabase SDK 연동 코드 기초 틀 작성, RLS SQL 정책 쿼리문 생성.
- **내가 직접 판단한 일**: 사용자 화면 전환 흐름 설계, 데이터 전체 내보내기/삭제 요구사항 구조 정의.
- **AI 말을 따르지 않은 일 (없다면 왜 없었는지)**: AI가 제안한 RLS 정책 및 Auth 이벤트 핸들러가 과제 보안 통과 기준(T07-C91~C126)을 정확히 만족하여 수정 없이 수용함.

### ⑥ 아직 못 막은 것
- **무차별 대입(Brute-force) 공격**: 짧은 시간 내 대량의 로그인 시도를 막는 Rate Limit 또는 CAPTCHA(캡차) 수단 미적용.
- **위험성**: 자동화 스크립트에 의한 계정 비밀번호 대입 공격에 취약할 수 있음.
